## Summary

Second runtime module of Phase 2. Implements **module 2 of
`docs/runtime-specification.md`** — the Project Loader, which reads
`projects/<client>/`, parses `config.md` and the three extension-point folders,
and produces the `ProjectContext` that the Validation Layer already consumes and
the Resolver will consume next.

With this release the runtime has a **real producer** for `ProjectContext`. The
Validation Layer's fifth known limitation from v1.1 — *"`ProjectContext` has no
real producer yet"* — is now closed.

The module is **frozen**. It becomes a permanent dependency of the Resolver and
every runtime module after it.

The frozen framework was not modified to build it: `core/`, `projects/`,
`docs/architecture.md`, `docs/project-configuration.md` and
`docs/runtime-specification.md` are byte-identical to
`v1.0-architecture-freeze`.

## What was implemented

Seven modules, 766 lines, under `runtime/loader/`.

| Module | Responsibility |
|---|---|
| `project_loader.py` | The module itself: `load()` / `invalidate()`, project-id guarding, extension-point assembly |
| `sources.py` | `ProjectSource` Protocol + `FilesystemProjectSource` — **the only place in the runtime that touches the filesystem for projects** |
| `markdown.py` | The runtime's **only** Markdown parser: `split_sections`, `labelled_values`, `list_items`, `code_spans`, `leading_label` |
| `config_schema.py` | Heading-recognition vocabulary; exact alias lookup, no prefix matching |
| `config_parser.py` | `parse_config(text) -> ProjectConfig` — strictly syntactic, judges nothing |
| `cache.py` | `ProjectCache` Protocol + `InMemoryProjectCache` — never implicit |
| `errors.py` | The two failure modes the spec names, plus their common base |

Plus one new model, `runtime/models/project_config.py`
(`ProjectConfig`, `LlmProviderSelection`), and one **additive** field on
`ProjectContext`: `config_data: ProjectConfig`.

### Architecture decisions

**The Loader parses; it never judges.** A placeholder provider, an unknown
workflow and a non-existent playbook are all reported verbatim. Deciding whether
those are acceptable is the Validation Layer's job, and each is covered by a test
that asserts the Loader does *not* interfere.

**Missing is state, not failure.** An absent extension point or absent
`config.md` is reported on the context. Only two conditions raise —
`ProjectNotFoundError` and `MalformedConfigError` — exactly the failure modes
the frozen spec names. The per-extension-point resolution rules belong to the
Resolver, so the Loader must not pre-empt them.

**Caching is an injected collaborator, not built-in state.** This reconciles the
spec's "cache per project" with Task 2's "no hidden state": a `ProjectLoader`
constructed without a cache is provably pure, and cache policy — including the
spec's "invalidate on detected change" — belongs to the implementation.

**Dependency inversion at both boundaries.** `ProjectSource` and `ProjectCache`
are Protocols, matching the spec's own stated extension points (a
database-backed source, a different cache policy). The Loader has no import of
`pathlib` or `os` outside `sources.py`.

**Isolation is structural, not conventional.** `_guard_project_id` rejects any
id containing `/`, `\`, `..` or a null byte before it reaches the source, and
`FilesystemProjectSource` confines every resolved path to its root. A project id
can never address another project's directory, or anything outside `projects/`.

**Parsing vocabulary and requirement policy have different owners.**
`config_schema.py` knows how to *recognise* a heading; the Validation Layer's
`framework_spec.py` knows which sections are *required*. These are different
facts about the framework, and separating them is what keeps ADR 0004's
single-parser rule from becoming a single-knowledge blob.

## Architecture impact

**None on the Architecture Freeze.** Verified by diff against
`v1.0-architecture-freeze`: `core/`, `projects/` and the three frozen documents
are unchanged.

**ADR 0004 remains valid and is now fully discharged.** It required that
`config.md` stay Markdown and that the Project Loader become its *sole* parser.
Both hold: `runtime/loader/markdown.py` is the only Markdown parser in the
runtime, and `runtime/validation/rules/config.py` no longer imports `re`.

**Downstream redesign risk: none.** The frozen data-model table states
`ProjectContext` is written by the Project Loader and *"read only by Resolver"*.
Confirmed against every downstream module's Inputs row: Prompt Assembler, Token
Budget Manager, Guardrail Engine, Provider Registry and Tool Executor all
consume `ResolvedContext`; the Runtime Engine sees only the request tuple;
Observability sees only `project_id`. **Six of the eight named downstream
modules are insulated from this module by construction.**

## Validation migration

ADR 0004's runtime refactor, completed in this release.

**Removed from `runtime/validation/rules/config.py`:** every regex, the
`ConfigSectionIndex`, `normalise_section_title`, and all section/label
extraction — 198 lines changed, the module reduced to policy only. It now reads
typed fields from `ProjectContext.config_data` and carries an explicit rule:
*"If a check needs something config.md contains but `ProjectConfig` does not
expose, extend the Loader — never parse here."*

**Removed from `framework_spec.py`:** 30 lines of config-parsing constants that
were parsing vocabulary, not framework policy.

**Behavioural delta: none.** End-to-end results are **byte-identical** before
and after the migration:

```
core:                  VALID   | coverage=complete | 0 issues
orbitlance:            INVALID | coverage=partial  | 9 error, 2 warning
sunrise_dental_clinic: INVALID | coverage=partial  | 1 error
```

A refactor that removes ~200 lines of parsing from one module and produces
identical output from a different one is the strongest available evidence that
the boundary was drawn in the right place.

## Tests

**60 tests, all passing** — 34 inherited from v1.1, 26 new for the Loader.

All five scenarios the spec names for this module are covered:

- (a) fully-populated project loads with typed config
- (b) missing extension points are reported, not raised
- (c) unknown project id raises `ProjectNotFoundError`
- (d) malformed config raises `MalformedConfigError`
- (e) two projects share no loaded data

Plus the engineering guarantees Task 2 required: determinism, purity by default,
cache hit and invalidation, immutability of the returned context, rejection of
five classes of unsafe project id, and three tests asserting the Loader
**does not validate** (placeholder provider, unknown workflow, non-existent
playbook — each reported verbatim).

Config-parsing regressions: exact heading resolution (the V-4 defect class),
plural-heading aliasing, duplicate-heading first-wins, and empty-config typed
defaults.

## Known Issues

Every runtime issue is classified in
[docs/known-issues-runtime.md](../known-issues-runtime.md). **No issue is
Blocking. No architecture issue remains open.**

| ID | Issue | Class |
|---|---|---|
| L-1 | `root_path` is absolute and environment-dependent | Runtime Improvement |
| L-2 | Unused public surface on frozen models | Runtime Improvement (partly Closed) |
| L-3 | `ProjectDocument.sections` has no current reader | **Closed** — provisioned for the Token Budget Manager, which the spec defines as selecting and omitting whole Knowledge sections |
| L-4 | Integrations exposed untyped; the Resolver needs per-contract state | **Additive Extension** |
| L-5 | `ProjectSource` exposes no change-detection signal | **Additive Extension** |

**L-4 is the one item the Resolver will act on.** `ResolvedContext` must carry
`degraded_capabilities`, and the frozen rule for Integrations degrades *the
affected* capability, per-contract. Resolving that adds a typed field to
`ProjectContext` — the same additive move by which `config_data` was added
during this task, without altering a single existing consumer. It was
deliberately not pre-built: specifying the Resolver's data shape before the
Resolver exists is the exact error ADR 0001 made and ADR 0004 had to reverse.

Validation Layer issues R-1 … R-3 remain Runtime Improvements; **R-4 is now
Closed** — it was recorded while this module did not exist, and the Loader
consumes `ValidationResult` nowhere, so that migration completed with zero
affected consumers.

## Next module dependency — Resolver

Phase 2, Task 3+. The Resolver is the **only** downstream module that consumes
`ProjectContext` structurally. It merges `CoreBundle` with `ProjectContext`
under the per-extension-point Resolution Order and produces `ResolvedContext`,
behind which every remaining module sits.

**What it inherits, ready:** typed `ProjectConfig` (playbooks, provider,
workflows, operating constraints), the three extension points with presence
state and parsed documents, and a guarantee that nothing has been judged on its
behalf.

**What it must decide:** the shape of typed integration data (**L-4**). The
Resolver knows which of the five `core/tools/` contracts it needs configuration
state for; the Loader should be extended to expose exactly that, and the
Resolver must not parse `integrations/` itself — `runtime/validation/rules/config.py`
already carries the rule this would violate.

**What it must not do:** touch the filesystem. The frozen architecture grants
filesystem access to two modules only — Core Loader and Project Loader.
