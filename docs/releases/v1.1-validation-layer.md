## Summary

First runtime module of Phase 2. Implements **module 13 of
`docs/runtime-specification.md`** — the Validation Layer, which verifies
structural and content-level correctness of Core and Project data before either
is used, at authoring time (CI) and at activation time (runtime).

The module is now **frozen**. It becomes a permanent dependency of the Project
Loader and every runtime module after it.

The frozen framework was not modified to build it: `core/` and `projects/`
are byte-identical to `v1.0-architecture-freeze`.

---

## Architecture decisions

**Validation reports; it never activates.** `ValidationResult` is a verdict, not
an action. The Runtime Engine owns the activation gate, per the frozen spec.

**Severity follows the per-extension-point resolution table**, not one uniform
rule. Missing Knowledge or Config blocks; missing Branding or Integrations
warns, because the framework defines safe degradation for those two and no safe
default for the first two.

**Absent collaborator ≠ satisfied check.** When the Provider Registry or a
CoreBundle is not supplied, the dependent rule does not run, is recorded as a
coverage gap, and the result cannot be `valid`. Silence is never substituted
for an answer.

**Dependency inversion at the module boundary.** The layer depends on a
`ProviderRegistryPort` Protocol, not on any provider or registry
implementation, so it shipped before the Provider Registry exists and remains
provider-independent.

**Open/Closed at the rule level.** A new check is a new class plus one
registration entry. No existing rule, the registry, the pipeline or the
validator is touched.

**Framework facts live in exactly one module.** `framework_spec.py` holds every
transcribed constant, each citing its source in `core/`. No rule hardcodes
framework structure, and no project name appears anywhere in the runtime.

## Major capabilities

**24 rules** — 18 project, 6 core.

| Area | Checks |
|---|---|
| Structure | project root, id naming convention, the four extension points |
| Knowledge | all 8 documents present, non-empty, free of unfilled placeholders |
| Config | required sections, playbook exists in Core, workflows are canonical, provider declared, provider registered, Operating Constraints additive-only |
| Extension points | branding content, coverage of all five tool contracts |
| Security | committed credentials across every project document |
| Core | 10 prompts, 3 guardrails, 6 workflows, 5 tool contracts, no playbook leakage, no client-specific content |

Every issue carries **code, severity, message, file, section, field and
recommendation**. There is no generic "validation failed" path — a
`ValidationIssue` with an empty mandatory field raises at construction.

Issue codes are a stable public contract; retired codes are never reused.

## Engineering guarantees

**Fails closed.** `valid` is conjunctive: no blocking issues **and** complete
coverage. Verified exhaustively — no construction of `Validator` yields
`valid=True` while a check silently did not run.

| Scenario | `valid` | coverage |
|---|---|---|
| all collaborators supplied, sound project | True | complete |
| no Provider Registry | False | partial |
| no CoreBundle | False | partial |
| unregistered provider (registry present) | False | complete |
| a rule raised | False | partial |

**Deterministic.** 20 runs with freshly constructed validators produced exactly
one issue ordering and one execution ordering. Issues sort on
`(severity rank, code, file, section)`.

**Never crashes on malformed input.** The module's one documented failure mode.
A rule that raises becomes an `ENGINE001` ERROR plus a `FAILED` execution
record — failing the project closed rather than passing it silently or taking
down the run.

**Never mutates what it validates.** Frozen dataclasses and read-only mappings
throughout.

**Skipped is never confused with passed.** Every rule produces a
`RuleExecution`. `SkipReason` separates *data absent and already reported*
(not a coverage gap) from *collaborator unavailable* (a real gap).

**Secrets are never echoed.** A detected credential is reported by type and
line number; the matched value is deliberately withheld so scanning cannot
copy it into logs or audit trails.

## Known limitations

1. **No filesystem adapter.** Per the spec, this layer validates a
   `ProjectContext`; producing one is the Project Loader's job. Until that
   ships, running the validator against real files requires a caller-supplied
   harness.
2. **Provider registration is unverifiable today.** No Provider Registry
   exists, so that rule is always skipped and every real project reports
   `coverage=partial`. This resolves automatically when the registry is
   injected — no code change here.
3. **All 8 knowledge documents are required.** Splitting them into critical vs.
   optional is noted in the runtime specification as a future refinement.
4. **Config is prose-parsed** (ADR 0001). Unconventional but reasonable
   markdown authoring can produce a false blocking error.
5. **`ProjectContext` has no real producer yet.** It was designed here and
   verified against real repository data via a harness, but the Project Loader
   is its first genuine consumer. A missing field would be an additive change,
   not a rewrite.
