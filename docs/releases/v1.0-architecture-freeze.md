## Architecture is considered frozen

As of this tag, the framework's structure and its runtime specification are frozen. Changes to `core/`, the extension-point contract, or the runtime module boundaries now require a deliberate decision and a version bump — they are no longer ordinary edits.

This milestone is **documentation only**. No architecture or framework file was modified to produce it.

---

## Core framework structure is finalized

`core/` is fixed at:

| Component | Count | Contents |
|---|---|---|
| Prompts | 10 | personality, mission, conversation rules, discovery, recommendation, lead qualification, consultation request, guardrails injection, fallback responses, tool instructions |
| Knowledge contracts | 8 | company, services, FAQ, process, technologies, pricing, portfolio, contact |
| Templates | 11 | 8 knowledge worksheets + branding, integrations, config |
| Workflows | 6 | discovery, recommendation, consultation, CRM sync, follow-up, voice agent |
| Guardrails | 3 | safety, escalation, compliance — loaded as one atomic bundle |
| Tool contracts | 5 | CRM, calendar, email, consultation form, general integrations |
| Industry playbooks | 6 + template | hotel, restaurant, logistics, healthcare, e-commerce, real estate |

The Core/Project override contract is settled: **six rules**, **four extension points** (Knowledge, Branding, Integrations, Config), and a per-extension-point missing-resource resolution table.

## Runtime specification is finalized

`docs/runtime-specification.md` defines **15 runtime modules** and **12 data models**, each module specified across 12 headings — purpose, responsibilities, non-responsibilities, inputs, outputs, public interface, internal/external dependencies, failure modes, validation rules, extension points, and unit test scenarios.

The module dependency graph is a verified DAG with Runtime Engine as the single root and no cycles.

The specification is written so an engineer can implement the runtime without making architectural decisions of their own.

## Cross-industry validation completed

The framework was exercised against multiple industries rather than assumed to generalize:

- **Six industry playbooks** authored covering hospitality, food service, logistics, healthcare, e-commerce, and real estate.
- **A fresh-eyes QA pass** simulated onboarding three unrelated businesses — a hotel, a restaurant, and a logistics company — using only the documentation. It surfaced **9 issues**, of which 2 were Critical. Reproducing the same defects across independent attempts confirmed they were systemic rather than incidental.
- Industry-specific behavioral limits (e.g. a healthcare agent must never diagnose) now have a defined runtime home via **Operating Constraints**, without weakening the reference-only rule for playbooks.

---

## Multi-project architecture validated

The "one framework, many clients" claim was proven rather than asserted:

- **Sunrise Dental Clinic** was built end-to-end using only the framework — all 8 knowledge documents, branding, integrations across all 5 tool contracts, and config — **without modifying a single file in `core/`**.
- Project isolation was verified: the project reads only from `core/` and itself, never from another project's folder.
- A second project (`orbitlance`) exists as a scaffold, confirming the structure supports projects at different completion stages.

## Known issues documented

`docs/known-issues.md` records **13 confirmed issues, all resolved**, each retained with its reasoning rather than deleted:

- **5** from the runtime architecture design and runtime specification (KI-1 … KI-5)
- **5** from the Final Design Review (FDR-1, FDR-2, FDR-4, FDR-5, FDR-6)
- **3** surfaced by the Architecture Freeze Sprint itself (FS-1 … FS-3)

**No open blockers remain.**

Two entries are worth carrying into implementation:

- **KI-5** widened Config's responsibility from pure selector to selector-plus-constraints. This was a deliberate, bounded trade-off — every alternative required breaking a frozen rule — and is documented as such rather than glossed over.
- **FS-1** was found *by* the consistency pass, then found *again* in a second section the first fix had missed. That recurrence is the clearest evidence the pass earned its place in the process.

## Implementation phase officially begins after this milestone

Recommended starting order, per the runtime specification:

1. Core Loader + Project Loader + Validation Layer — make loading bulletproof before anything depends on it.
2. Prompt Assembler with a single LLM provider adapter — get one project talking end-to-end.
3. Guardrail Engine (pre-flight + post-response) — **before any real user traffic**, non-negotiable.
4. Discovery → Recommendation → Consultation workflow state machines.
5. Calendar + CRM Tool Executors.

### Carried into implementation, not blocking the freeze

- Both projects' `LLM Provider` fields are placeholders. This is correct today — the Provider Registry doesn't exist yet — but the Validation Layer must reject a placeholder before activation. That rule is already specified and should be among the first validation checks built.
- Runtime Engine's `handleRequest` must be built as injected, ordered pipeline stages rather than one function body, with the guardrail stages non-removable. Decided during the freeze sprint to avoid a single-file merge bottleneck once multiple engineers contribute.
