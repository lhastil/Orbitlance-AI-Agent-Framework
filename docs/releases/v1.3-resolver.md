## Summary

Third runtime module of Phase 2. Implements **module 3 of
`docs/runtime-specification.md`** — the Resolver, which combines a `CoreBundle`
with a raw `ProjectContext` per the Resolution Order in
`docs/project-configuration.md` and produces the `ResolvedContext` that every
module downstream consumes.

The module is **frozen**. `ResolvedContext` is now the runtime's real downstream
contract: the Prompt Assembler, Token Budget Manager, Guardrail Engine, Tool
Executor and Provider Registry all read it, and none of them ever sees a raw
`ProjectContext`.

`core/`, `projects/` and the three frozen documents are byte-identical to
`v1.0-architecture-freeze`.

### Resolution Order, per the frozen specification

The table is deliberately **not uniform** — the framework states that applying
one rule to all four extension points would be unsafe — so it is implemented as
four independent rules rather than a chain of conditionals.

| Extension point | If missing | Implemented behaviour |
|---|---|---|
| **Knowledge** | Fail loudly at activation | `knowledge_incomplete = true`; nothing invented, nothing substituted |
| **Branding** | Core's neutral default voice | Overlay resolves empty; decision recorded (see R3-3) |
| **Integrations** | Degrade the affected capability | Every Core capability disabled, per-tool |
| **Config** | Documented defaults | No playbook selected; all workflows enabled |

**Every set the rules need is derived from `CoreBundle`, never transcribed** —
required knowledge from `core/knowledge/`, the workflow vocabulary from
`core/workflows/`, the capability set from `core/tools/`. The module imports no
framework constant and never imports the Validation Layer, which would have
inverted the frozen dependency direction.

**Fail-closed where completeness is unknowable.** A `CoreBundle` declaring no
knowledge contracts yields `knowledge_incomplete = true` rather than a silent
pass — the V-1 defect class, avoided by construction and covered by a test.

**The Resolver judges nothing.** Placeholder providers, unknown workflows and
non-existent playbooks are carried verbatim and recorded. Deciding whether they
are acceptable remains the Validation Layer's job.

**A pure function with no process control.** It never mutates its inputs, never
calls a provider, never touches the filesystem, and never decides whether a
project activates — the Runtime Engine owns the gate that reads
`knowledge_incomplete`.

## R3-1 — resolved by aligning Validation with the Core template

The independent gate found that the Validation Layer accepted three workflow
spellings the Resolver drops: `Consultation Request`, `CRM Synchronization`,
`CRM Synchronisation`. A project using one passed validation and then lost that
workflow from `ResolvedConfig.enabled_workflows`.

**The divergence was in Validation, not the Resolver.**
`core/templates/config.md` sanctions six spellings and none of the three. The
Resolver derives its vocabulary from `core/workflows/` and transcribes nothing,
so it already followed the frozen template; `WORKFLOW_ALIASES` is the
transcription that had drifted.

**Fixed at the authoritative owner:** the three entries were removed from
`runtime/validation/framework_spec.py`. Nothing was added to the Resolver.

Measured before changing anything: exactly those three entries were
load-bearing, no existing project declares any of them, and end-to-end
validation output is unchanged. `tests/test_vocabulary_alignment.py` now
asserts exhaustively that everything Validation accepts, the Resolver also
resolves — the two can no longer drift apart without a test failing.

## Next module dependency

`ResolvedContext` is the input to the Prompt Assembler, Token Budget Manager,
Guardrail Engine, Tool Executor and Provider Registry. Two contracts those
modules must know:

- **R3-3** — an empty `ResolvedContext.branding` means "Core's default voice
  applies", never "branding data is missing and must be sourced".
- **R3-2** — no module currently owns `ResolvedContext` caching. The Runtime
  Engine or the first consumer should claim it deliberately.
